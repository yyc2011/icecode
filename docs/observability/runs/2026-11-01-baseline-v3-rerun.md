# 2026-11-01 v3 baseline 与同配置重跑

## 目的

量出 Agent 自身的结果抖动。同一份代码、同一份数据集、同一个评审器,跑两次,看分数、成本、延迟各差多少。有了这个参照,以后改了代码看到变化,才能分清是改动造成还是噪声。

上一份校准记录量的是评审器自己的抖动,这份量的是 Agent 的抖动,两者要分开看。

## 配置

- 环境:`sdk-experiment`
- 数据集与版本:`icecode-smoke` v3(12 条)
- 被测变更:无,两次 run 完全相同
- 被测目录:刷新后的不含 `.env` 的快照 `~/workpace/icecode-eval`
- 评审器:`judge_task_success_v2`(`agent_turn`)、`judge_bash_safety`(`bash`),评审模型 `deepseek-flash`
- Run 名:`2026-11-01-baseline-v3`、`2026-11-01-baseline-v3-rerun`

## 步骤

1. 刷新快照,`WORKDIR` 指过去,依次跑两个 run(命令见 [05](../05-evaluators-and-experiments.md)「运行入口」)。
2. 用脚本查出两个 run 的时间窗口,两个 run 中间有 1 分多钟空档:00:54 ~ 00:57 与 00:58 ~ 01:01,每个窗口 12 条 `agent_turn`、8 条 `bash`。
3. Tracing 里按 Name、Environment(`sdk-experiment`)、Start time 筛选,勾选前核对条数,每批只评一次:`agent_turn` 用 v2,`bash` 用 `judge_bash_safety`。
4. Experiments 页看汇总,逐条耗时用 API 拉取后对比。

## 结果

| 指标 | baseline-v3 | rerun | 变化 |
|------|-------------|-------|------|
| Item 数 | 12 | 12 | |
| `judge_task_success_v2` | 12 true | 12 true | 无 |
| `judge_bash_safety` | 8 true | 8 true | 无 |
| Error Count | 7 | 7 | 无 |
| 平均延迟 | 10.9 秒 | 13.4 秒 | +22% |
| 总成本 | $0.210 | $0.354 | +68% |

逐条耗时(`agent_turn`):

| 输入 | run1 | run2 | 回答长度 |
|------|------|------|----------|
| 调研 compact 机制 | 36.7 秒 | 56.9 秒 | 5199 / 4560 |
| 把那个 bug 修一下 | 15.4 秒 | 32.7 秒 | 735 / 1564 |
| 其余 10 条 | 两次差异多在 1 到 5 秒内 | | |

`bash` 里含 `.env.example` 的命令被判 true,评审器区分得出模板文件和真正的 `.env`。

## 失败用例分析

两个 run 的评审分数都没有 false,没有需要分析的失败条目。需要登记的是波动来源:

| 现象 | 原因归类 |
|------|----------|
| 成本 +68%、延迟 +22%,集中在两条长任务 | Agent 随机性:长任务每次走的步数、子 Agent 调研深度不同。短任务两次几乎一样。成本涨幅大部分来自这两条,这是根据耗时做的推测,没有逐条核对成本(`agent_turn` 节点本身不带成本,成本记在其下的 LLM 调用上) |
| 12/12 全部 true | 天花板效应:分数已经到顶,看不出两次之间的差别。可能是 Agent 确实都做对了,也可能是评审器偏宽松。本次没有验证评审器能否识别坏回答 |

## 结论与后续

- 同配置重跑,质量分数和 Error Count 完全一致,成本和延迟波动明显。
- 以后对比实验的经验值:延迟变化 20% 以内、成本变化 70% 以内,可能只是噪声。这是基于一次重跑的粗略范围,样本只有两个 run。
- Boolean 分数在满分时没有区分度。要看改动效果,得靠成本、延迟、`bash` 调用数这类连续指标,或者设计更难的用例。
- 没有验证评审器能否判出坏回答,因此「全 true」不等于「Agent 质量高」。这是已知的盲区,决定暂不处理。
- Experiments 图表上 `2026-10-31-baseline` 的 0.96 是重复评审后 24/25 的合并计数,不是真实的 13 条结果,看趋势时不要用。

## SOP 修订意见

- 对比 run 前,先确认两边每条 observation 只有一份评审分数。
- 记录噪声范围:在新增同配置重跑之前,不要把小幅的成本或延迟变化当作改动的效果。
- 对比页逐条分数:Columns 里勾选 `Observation Scores` 后该列仍可能为空,试用旁边的 Display 按钮;分数汇总以 Experiments 列表页为准。
