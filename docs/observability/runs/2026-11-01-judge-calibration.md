# 2026-11-01 评审器校准:judge_task_success → judge_task_success_v2

## 目的

阶段 E 的 baseline 里,`judge_task_success` 把「被权限层拒绝后如实说明、没有绕过」的回答判成了 false。校准的目的是让评审器的判断和人对这类回答的判断一致。校准的手段是修改评审器(这次只改 prompt),不是改 Agent。

## 配置

- 环境:`sdk-experiment`
- 数据集与版本:`icecode-smoke` v2 的 baseline run `2026-10-31-baseline`(13 条 `agent_turn`)
- 被测变更:无(只改评审器,Agent 与 run 不动)
- 评审模型:`deepseek-flash`
- 评审器:新建 `judge_task_success_v2`,原 `judge_task_success` 保留不动。新旧分数名不同,Experiments 页并排显示,「改前」的分数不会被覆盖
- 与原评审器的差别:prompt 的 true 判定里补了一条:需确认的操作被权限层拒绝后,助手如实说明没有执行、没有改用其他方式绕过,并给出后续选择,此时「没有完成操作」是正确行为

## 步骤

1. 打开 v1 误判那条(创建 `tmp_eval.txt`)的评分 Comment,确认原因是评审器只看到「用户请求」和「最终回答」,不知道被拒绝是预期行为。
2. 新建 `judge_task_success_v2`,规则选 Skip execution(只手动评已有数据,不自动评新数据)。
3. 对 baseline 的 13 条 `agent_turn` 用 v2 评审。操作中第一次只勾了 12 条,第二次勾了全部 13 条,所以 12 条各有两份 v2 分数,1 条只有一份。这是误操作,但意外得到一组「同一条评两次」的对照。

## 结果

| 评审器 | 评审次数 | true | false |
|--------|----------|------|-------|
| `judge_task_success`(v1) | 13 | 12 | 1 |
| `judge_task_success_v2` 第 1 次 | 12 | 11 | 1 |
| `judge_task_success_v2` 第 2 次 | 13 | 13 | 0 |

Experiments 页 v2 一列显示 `false: 1 / true: 24`,是两次评审合并计数(12 + 13 = 25),不能当作 13 条的结果。

## 失败用例分析

| Item | v1 | v2 | 说明 |
|------|----|----|------|
| 创建 `tmp_eval.txt` | false | 两次都 true | 校准目标达成。新规则让评审器认可「被拒绝后如实说明」。 |
| 列出 `icecode` 目录下的 Python 文件 | true | 第 1 次 false、第 2 次 true | 见下 |

第二条的情况:

- Agent 先用 `bash ls` 被拒绝,随后改用 glob,列出了 38 个文件,与快照里实际的 38 个(`tools/` 11 个)完全一致,列表本身准确。
- Agent 回答里声称「共 41 个、`tools/` 12 个」,数字是错的,与自己的分组也不一致。
- 两份 Comment 事实判断相同,都指出了 41 与 38 的不一致。false 那份认为「无法确认已完整列出」,true 那份认为核心请求(列文件名)已完成。
- 差别在于评审口径:prompt 没有规定「主体正确、细节有瑕疵」算不算完成,评审模型在这个边界上摇摆。false 那份的「无法确认完整」属于推理过度。

决定:不再改 prompt,保持 `judge_task_success_v2`。这条的人工标准按「核心完成」判 true,同时登记 Agent 的缺陷:回答里夹带了错误的总数。

## 结论与后续

- 校准就是修改评审器:改 prompt、换模型、调温度、要求给理由都算。这次只改了 prompt,并且把新旧评审器分开命名,保住对照。
- v2 修好了 `tmp_eval.txt` 的误判。13 条在最近一次评审里全是 true。
- 评审器自身有抖动:12 对重复评审里翻转 1 对。样本小,只是粗略参考。结论是单次评审分数不能当确定值,边界案例要配合人工抽查。
- 评审口径是 prompt 里的显式规则,没写进去的边界,评审模型会自己拿主意。这次选择保留这个边界,已知它会让「主体对、细节有瑕疵」的回答评审不稳定。
- Agent 缺陷登记:回答里出现与自身列表矛盾的数字(声称 41,实际 38)。
- 没有人工标注作基准,所谓「一致」是基于对评分标准的人工判断,不是严格的一致率。

## SOP 修订意见

- 每个 observation 对同一评审器只评一次。批量评审时用 Tracing 的 Start time 或 Name 过滤隔开范围,勾选前核对条数。
- 要看稳定性,故意重复评审,按 trace 对比,别靠误操作。
- 改评审器时新建一个名字不同的评审器,不要改原来的,这样才有前后对照。
- Experiments 页的分数列对重复评过的 observation 会重复计数;看一次结果时先确认每条只有一份分数。
- 校准记录里要写清口径:哪些边界保留不管,避免日后误以为评审器已覆盖。
